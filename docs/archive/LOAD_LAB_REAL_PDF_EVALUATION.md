## truckerjson vs critical_v1_1 comparison

**Latest run (all six PDFs, both contracts, full table + executive summary):** see `docs/LOAD_LAB_CONTRACT_COMPARISON_REPORT.md` (generated by `tools/run_load_lab_contract_pair_eval.py`).

**Purpose:** Run the **same real-PDF set** under **legacy** (`truckerjson`, default) and **dispatch-critical** (`critical_v1_1`, explicit query param) and record a **field-by-field** review. This section is a **comparison report** only — no new parser architecture in this step.

**Important — do not mix learning rows:** When pulling `extraction_field_learning_events` for a run, always filter by `response_contract` (e.g. `truckerjson` vs `critical_v1_1`) **or** restrict to a single batch by `created_at` / monotonic `id` per `field_path`. Unfiltered lists will **interleave** two contracts after two semantic passes on the same run.

**How to run both contracts on the same PDF (Load Lab run):**

1. For each `run_id` in the evaluation set, call:
   - `POST /api/v1/load-lab/runs/{run_id}/semantic-extract?force=true&response_contract=truckerjson`
   - then `POST /api/v1/load-lab/runs/{run_id}/semantic-extract?force=true&response_contract=critical_v1_1`  
2. The run row’s `parse_response` in the database holds only the **last** successful extract. For a saved side-by-side:
   - **Option A (recommended):** After **each** POST, copy `parse_response` (and, for `critical_v1_1`, confirm `context.critical_extraction_v1_1` and `parse_diagnostics.critical_extraction_v1_1_guardrails`) to a named JSON file, e.g. `run_{id}_truckerjson.json` / `run_{id}_critical_v1_1.json`.
   - **Option B:** Use `GET .../field-learning-events?response_contract=truckerjson&dedupe=true` and the same for `critical_v1_1` to compare `proposed_value_json` by `field_path` (coverage matches whatever the snapshot records; re-semantic may be needed for newly added paths such as stop `street` / appointment fields).
3. In-container diff helper (same tenant, same run IDs, both contracts present):
   - `python -m app.scripts.compare_load_lab_contracts_eval --tenant-id 53 --run-ids 38,39,40,41,42,43`

**Per-field (or per-stop-field) marks — use one of:**

| Mark | When to use |
|------|-------------|
| **correct** | Matches PDF / dispatch ground truth, plausible, no conflict with special checks below. |
| **wrong** | Contradicts PDF, nonsense, or violates a special check. |
| **missing** | Null / empty when a value is expected, or explicitly suppressed. |
| **needs_review** | Ambiguous, partial, inconsistent, or weak evidence; **use for partial addresses** (city only, etc.). |
| **guardrail_changed** | Value (or null) differs **because** of `critical_extraction_v1_1` guardrails or a logged guardrail event (see `parse_diagnostics.critical_extraction_v1_1_guardrails`). |
| **safer_than_legacy** | **yes / no** — for that field, is `critical_v1_1` **strictly better or equal** on safety (wrong answers worse than null)? Decided by reviewer; not automated in this document. |

**Special checks (must be explicit in the written report for each PDF):**

1. **Broker load reference — nonsense tokens**  
   `broker_load_reference` must **never** be accepted as high-confidence if it is (non-exhaustive) prose junk such as: `Yes`, `RELATES`, `will`, `must`, `Information`, or similar non-reference words seen in past evals. Mark **wrong** for legacy if present; for critical, **missing** or null is **acceptable and often safer** than **wrong**.

2. **Uncertainty**  
   If `critical_v1_1` is uncertain, **blank/null is acceptable and better than a wrong** string for references and fragile fields.

3. **Pickup / delivery must not be broker-office / back-office**  
   Stops must **not** be sourced from **broker office**, **bill-to**, **remittance**, **payment**, **carrier**, **invoice**, **mailing**, or **corporate** address blocks. If either contract puts a stop there, mark **wrong** / **needs_review** and describe.

4. **Multi-stop PDFs**  
   `stops[]` **order** must match the real pickup/delivery sequence in the document; flag any reordering.

5. **Partial addresses**  
   If only city, only state, or fragmentary line, mark at least **needs_review** (even if not “wrong”).

6. **No mixed rows in the report**  
   Tables must be “all `truckerjson`” vs “all `critical_v1_1`” columns, or two clearly labeled sub-tables. Do not average or merge learning events across contracts in one row without a `response_contract` filter.

**Interpreting toward a future default:**

- `critical_v1_1` is a candidate for **default** only if, across this PDF set, it is **at least as safe** on broker ref + stop geography + money fields, and **not systematically worse** on omissions (blanks where legacy was wrong are usually a win; blanks where truth was extractable are not).
- **Final call:** product/dispatch; **this document does not change** `response_contract` defaults in code or API.

## Current known issues surfaced by this evaluation

### 1) Broker identity diagnostics are picking a non-company header string
`parse_diagnostics.broker_identity_selection_reason` is currently driven by the top of `broker_confidence_matrix` (when no MC/DOT grounding exists). For `JBHunt.pdf` it selected:

- `Attachment to Broker Carrier Agreement`

This suggests `party_mentions` is capturing a **document title/header** string as a “company-like” party mention, and the broker matrix is scoring it highly.

**Impact:** broker identity diagnostics can be misleading even when the extracted broker name is correct.

### 2) Reference acceptance is admitting obvious non-reference tokens
- `primary_reference_selection_reason` chose `shipment_number='Yes'`
- Deterministic reference extraction is matching too broadly on “Shipment …” lines and pulling tokens like `Yes` / `Inaccuracy`.

**Impact:** reference diagnostics and `extracted.references[]` become noisy, even if `broker_load_reference` is correct.

### 3) Guarded mode introduced a date misclassification
- In guarded mode, a date `03/06/2026` surfaced as `pickup_number` inside `extracted.references[]`.

**Impact:** shows a leak of date-like strings into structured references (should be rejected as non-reference).

### 4) Phone number hallucination
- `broker_contact_phone_snapshot = +1(999)-999-9999` appears in 2 modes, but it is not grounded in PDF text.

**Impact:** should be cleared unless present in PDF/email thread surfaces (or explicitly marked as a directory suggestion with correct provenance).
